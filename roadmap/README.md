## 마일스톤

### M1. 배포 가능한 신뢰 경계

목표는 실제 MySQL·Redis·Docker와 두 클라이언트를 묶었을 때 인증, 매칭, 제출, 종료가 일관되게 동작하는 상태다.

- `REL-01`: 실 인프라 AI/PvP E2E
- `API-01`: 요청·응답 DTO와 단일 오류 계약
- `EXEC-02`: AI 작업공간 ownership·만료·고아 정리
- `EXEC-03`: 플레이어·심판 프로세스 간 격리와 공정성
- `MATCH-01`: 비동기 실행과 명시적 매치 상태 머신
- `MATCH-02`: 다중 인스턴스 매칭 원자성
- `MATCH-03`: 다중 소켓과 disconnect/cleanup 안정성
- `SEC-01`: 쿠키 인증 CSRF·rate limit·비밀 정책
- `DATA-01`: DB 마이그레이션과 제약조건

완료 조건:

- join/cancel/동시 submit/disconnect가 실 Redis에서 결정적으로 통과한다.
- 엔진과 DB 저장은 매치당 최대 1회이며 실패 상태가 유실되지 않는다.
- 사용자 코드가 상대 코드나 심판 프로세스를 읽거나 변경·종료할 수 없다.
- 실행되지 않고 중단된 AI 매치도 보존 상한 이후 작업공간과 소유권 정보가 남지 않는다.
- 모든 REST 오류가 같은 JSON 스키마를 사용하고 내부 예외 문구를 노출하지 않는다.
- 배포 스키마는 자동 `update`가 아니라 버전 관리된 migration으로 재현된다.

### M2. 관측 가능하고 회귀에 강한 운영

- `OPS-01`: 구조화 로그, metric, health, alert
- `TEST-01`: Testcontainers·브라우저 E2E·CI 품질 게이트
- `AUTH-01`: 실제 Google OAuth smoke와 계정 정책
- `DATA-02`: 제출 코드·리플레이 보존 및 개인정보 정책

완료 조건:

- queue 대기 시간, 매치 성공률, 엔진 시간/timeout, Redis 잔존, DB 저장 실패를 dashboard에서 확인할 수 있다.
- 장애 시 correlation ID로 브라우저 요청부터 엔진 실행·DB 저장까지 추적할 수 있다.
- 실제 OAuth 공급자와 주요 브라우저에서 로그인·로그아웃·쿠키 정책이 검증된다.

### M3. 기능 단위 유지보수 구조

- `FE-01`: GameArena 상태/화면 분리
- `FE-02`: 소켓 재연결·오류 UX
- `BE-01`: 엔진 결과 타입과 단일 결과 정책
- `EXEC-01`: 실행 정책의 설정·버전·감사 가능성

완료 조건:

- 페이지가 네트워크 프로토콜과 매치 상태 머신을 직접 구현하지 않는다.
- AI/PvP/crash/draw/disconnect 결과가 하나의 정책과 결과 행렬 테스트를 사용한다.
- 실행 자원 정책과 엔진 이미지 버전이 설정·로그·결과 메타데이터에 남는다.

### M4. 플랫폼 현대화와 용량 최적화

- `DEV-01`: CRA에서 유지보수되는 빌드 도구로 전환
- `OPS-02`: CI/CD와 공급망 검증
- `SCALE-01`: 부하·용량 측정 후 실행 비용 최적화

이 마일스톤은 M1~M3의 검증 자산을 선행 조건으로 한다. 코드 실행 격리를 약화시키는 성능 최적화는 허용하지 않는다.

## 진행 규칙

1. 작업 시작 전 `backlog.md`의 근거와 완료 조건을 확인한다.
2. 구조 변경과 동작 변경은 별도 커밋으로 유지한다.
3. 각 작업은 관련 자동 테스트, 장애 재현, 운영 문서를 함께 변경한다.
4. 완료된 항목은 이 폴더에서 삭제하지 않고 상태를 `DONE`으로 바꾸고 완료 커밋과 문서 링크를 기록한다.
5. 새로운 작업은 증상·근거·영향·검증 방법 없이 추가하지 않는다.
